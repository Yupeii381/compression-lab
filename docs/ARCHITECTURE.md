# Устройство приложения

Практическое руководство по каждому модулю, собственным изменениям и рабочему
примеру Хаффмана: [DEVELOPER-GUIDE.md](DEVELOPER-GUIDE.md).

Точка входа `Program.cs` вызывает `LabApplication.RunAsync`. Другой код не должен
зависеть от способа запуска: из IDE, через EXE, из другой рабочей папки или в CLI.
Контракт HTTP и формат `.clcs` сохранены после рефакторинга.

## Основные границы

| Каталог / тип | Ответственность |
|---|---|
| Web/Hosting/LabApplication | Сборка зависимостей, запуск сервера, открытие браузера, CLI |

| Web/Endpoints | Преобразование HTTP-запросов/ответов, без логики сжатия и сохранения |
| Web/Middleware | Проверка локального Host/Origin, заголовки, ошибки валидации |
| Web/Services/FileService | Потоковая загрузка, SHA-256, тестовый файл |
| Web/Services/ArchiveService | Временные файлы и восстановление загруженного архива |
| Web/Services/ExportService | Экспорт согласованного снимка результатов |
| Web/Services/ExperimentValidator | Проверка плана, заполнение параметров и версий кодеков |
| Web/Services/JobQueue | Отмена и переходы состояния активной задачи |
| Web/Services/LabWorker | Цикл выполнения задач, передача файлов в ядро |
| Web/Storage/LabRepository | Блокировка каталога, снимки и атомарная запись state.json |
| Web/Storage/LabPaths | Все пути внутри каталога данных, проверка идентификаторов |

| Core/Archives/ArchiveFormat | Бинарная структура CLCS0001 и проверка границ |
| Core/Archives/CodecPipeline | Прямой и обратный проход по цепочке |
| Core/Benchmarking/BlockBenchmark | Прогрев, повторы, замеры и проверка блоков |
| Core/CodecRegistry | Каталог, параметры и версии кодеков |
| Core/Plugins/PluginLoadContext | Зависимости внешних DLL и общий Contracts |

| Web/Updates/UpdatePackage | Проверка путей и распаковка нового выпуска |
| Web/Updates/UpdateService | Состояние проверки/загрузки и подготовка перезапуска |

Зависимости направлены от Web к Core и Contracts. Кодеки зависят от Contracts,
но не от Web. Ядро не обращается к HTTP, состоянию очереди и пользовательским каталогам.
Исходники стороннего LZMA SDK в Vendor не изменены и исключены из форматирования.

## Работа с состоянием

Состояние не выставляется наружу как общий изменяемый список. Repository возвращает
снимок массивов с записями Job/LabFile. Изменение задачи заменяет запись через `with`.
Новый JSON сначала записывается во временный файл и заменяет основной, затем
обновляется состояние в памяти. Все изменения сериализуются внутренней блокировкой.

Цепочки нормализуются в новые массивы/словари при постановке в очередь: последующее
изменение запроса не влияет на задачу. Снимки используются только для чтения;
вложенные параметры кодеков и массивы измерений не следует изменять.

Токен отмены принадлежит JobQueue и не сериализуется. Отмена пользователем и остановка
хоста различаются: при остановке работа возвращается в очередь, при пользовательской
отмене сохраняется cancelled. Состояние running после аварии возвращается в queued.
Тесты фиксируют эти переходы, включая отмену одновременно с остановкой.

## Куда вносить изменения

- Новый кодек: отдельный проект с ICompressionCodec; сервер и ядро менять не нужно.
- Новая операция HTTP: обработчик в Endpoints и сервис, если есть прикладная логика.
- Новый способ хранения: LabRepository; файловые пути остаются в LabPaths.
- Другая очередь/приоритеты: JobQueue + LabRepository, выполнение оставлять LabWorker.
- Новая версия контейнера: ArchiveFormat, с отдельной совместимостью чтения.
- Другие замеры: BlockBenchmark и BenchmarkResult, не обработчики HTTP.
- Изменение запуска/публикации: StartupOptions, LabApplication и PublishProfiles.

Основные проверки: SelfTest (кодеки/ядро/сервисы), http-smoke.ps1 (контракт HTTP),
release-smoke.ps1 (реальный самостоятельный EXE, встроенная среда, другая рабочая
папка, перезапуск, CLI и загрузка DLL). В Fixtures есть архив из прежней версии.
update-integration.ps1 проверяет реальное обновление EXE и откат на локальном сервере.
